O que é um banco de dados?

Um banco de dados é um conjunto organizado de dados, guardado de forma estruturada para que possam ser armazenados, consultados, alterados e apagados de maneira confiável — sem depender de arquivos soltos tipo planilhas ou textos.

📦 Organização

Os dados são guardados em estruturas previsíveis (tabelas), não em arquivos avulsos.

🔒 Confiabilidade

Regras garantem que os dados fiquem consistentes mesmo com vários acessos ao mesmo tempo.

🔍 Consulta

É possível buscar, filtrar e cruzar informações de forma rápida através de uma linguagem, o SQL.

💡
Analogia: pense num arquivo de gavetas de um escritório, só que digital — cada gaveta é organizada por categoria, tem etiquetas e um sistema que sabe exatamente onde cada papel está.

O que é um SGBD?

SGBD (Sistema Gerenciador de Banco de Dados) é o software que fica entre você (ou sua aplicação) e os dados guardados fisicamente no disco. Você nunca mexe nos dados diretamente — sempre pede para o SGBD fazer isso por você.

Armazenamento

Organiza fisicamente onde e como os dados ficam salvos.

Controle de acesso

Define quem pode ler, escrever ou apagar cada informação.

Integridade

Garante regras como "e-mail não pode se repetir".

Concorrência

Permite vários usuários acessando ao mesmo tempo sem corromper dados.

Exemplos de SGBD: PostgreSQL, MySQL, SQL Server, Oracle, SQLite. Este guia usa o PostgreSQL, um SGBD relacional, open-source e muito usado no mercado.

Diagrama Entidade-Relacionamento (DER)

Antes de criar a primeira tabela, é assim que se planeja um banco de dados: um DER é um desenho que representa as entidades (futuras tabelas), seus atributos (colunas) e como elas se relacionam entre si — tudo isso sem escrever uma linha de SQL.

🧩 O que ele mostra

As entidades do sistema, seus atributos principais, a chave primária de cada uma e os relacionamentos (com cardinalidade) entre elas.

🎯 Por que é importante

Planejar no papel é muito mais barato que corrigir uma tabela em produção. Evita retrabalho, revela problemas de modelagem cedo e serve como documentação viva do sistema.

🗣️ Facilita comunicação

É a linguagem comum entre quem programa e quem entende o negócio — dá pra validar as regras antes de implementar.

Como criar um DER

  1. Identifique as entidades — os "substantivos" do sistema: usuário, pedido, produto...
  2. Liste os atributos de cada entidade — o que precisa ser guardado sobre ela.
  3. Defina a chave primária — o que identifica cada registro de forma única.
  4. Trace os relacionamentos entre as entidades e defina a cardinalidade de cada um.
  5. Desenhe — no papel ou em ferramentas como draw.io, dbdiagram.io, brModelo ou o próprio pgAdmin.

Boas práticas

✅ Nomeie com clareza

Nomes de entidades no singular na modelagem (Usuário, Pedido) — cada um vira uma tabela depois.

✅ Um atributo, um valor

Evite colunas que guardam vários valores juntos (ex: "telefones" separados por vírgula).

✅ Cardinalidade explícita

Toda linha de relacionamento deve deixar claro se é 1:1, 1:N ou N:N.

✅ Valide com o negócio

Confirme as regras com quem entende o processo antes de implementar no banco.

Como vincular uma tabela a outra

No DER, uma linha conectando duas entidades representa um relacionamento. A forma de implementar esse relacionamento no banco depende da cardinalidade — o próximo capítulo mostra como criar essas colunas na prática, mas o conceito é este:

Um para um (1:1)

1 usuário tem no máximo 1 perfil, e vice-versa.

Um para muitos (1:N)

1 usuário pode ter vários pedidos; cada pedido é de 1 usuário só.

Muitos para muitos (N:N)

Vários pedidos têm vários produtos, e vice-versa.

💡
"Muitos para um" (N:1) é a mesma relação que 1:N, só vista do outro lado: muitos pedidos pertencem a um único usuário. É sempre a mesma linha do diagrama, lida em duas direções.
1_para_1.sql — a chave estrangeira recebe UNIQUE
CREATE TABLE tb_perfis (
    id_perfil SERIAL PRIMARY KEY,
    cd_usuario INTEGER UNIQUE REFERENCES tb_usuarios(id_usuario),
    tx_bio TEXT
);
✓ cada usuário só pode aparecer 1 vez em "tb_perfis" — isso garante o 1:1.
1_para_n.sql — a chave estrangeira fica na tabela "muitos"
CREATE TABLE tb_pedidos (
    id_pedido SERIAL PRIMARY KEY,
    cd_usuario INTEGER REFERENCES tb_usuarios(id_usuario),
    vl_total NUMERIC(10,2)
);
✓ sem UNIQUE — o mesmo cd_usuario pode se repetir em vários pedidos.
n_para_n.sql — precisa de uma tabela associativa
CREATE TABLE tb_itens_pedido (
    cd_pedido INTEGER REFERENCES tb_pedidos(id_pedido),
    cd_produto INTEGER REFERENCES tb_produtos(id_produto),
    nr_quantidade INTEGER NOT NULL,
    PRIMARY KEY (cd_pedido, cd_produto)
);
✓ "tb_itens_pedido" liga tb_pedidos e tb_produtos — uma linha por combinação.
⚠️
O PostgreSQL não tem um jeito direto de fazer N:N entre duas tabelas — sempre é necessária uma tabela associativa (também chamada de tabela pivô ou de junção) no meio, com uma FK para cada lado.

Tipos de dados

Cada coluna precisa de um tipo, que define que tipo de valor ela aceita e quanto espaço ocupa.

TipoUso

Boas práticas: nomes com prefixo

Além das convenções já vistas (snake_case, plural nas tabelas), muitas empresas adotam um padrão ainda mais explícito: um prefixo de 2 letras no nome de cada coluna, indicando o tipo de dado que ela guarda. Tudo sempre em minúsculo. Isso deixa o significado do dado visível só de olhar o nome — sem precisar abrir a estrutura da tabela.

PrefixoUsoExemplo
tb_Nome de tabelatb_usuarios
id_Identificador sequencial — chave primária da própria tabelaid_usuario
cd_Código — chave estrangeira, referenciando outra tabelacd_usuario
vl_Valor — números reais/decimais (dinheiro, medidas)vl_salario
nr_Número — valores inteirosnr_idade
tx_Texto — strings em geraltx_descricao
fl_Flag — valores booleanos (verdadeiro/falso)fl_ativo
dt_Data — datas ou data e horadt_nascimento

Juntando tudo em uma tabela real:

tabela_com_prefixos.sql
CREATE TABLE tb_pedidos (
    id_pedido SERIAL PRIMARY KEY,
    cd_usuario INTEGER REFERENCES tb_usuarios(id_usuario),
    vl_total NUMERIC(10,2) NOT NULL,
    nr_itens INTEGER NOT NULL,
    tx_observacao TEXT,
    fl_pago BOOLEAN DEFAULT false,
    dt_criacao TIMESTAMP DEFAULT NOW()
);
✓ CREATE TABLE — basta ler os nomes das colunas pra saber o tipo de cada uma.
💡
A regra de ouro é a consistência: escolhido o padrão, ele precisa valer para todas as tabelas do banco — sempre minúsculo, sempre o mesmo prefixo para o mesmo tipo de dado, do início ao fim do projeto.

Como criar uma tabela

A tabela do capítulo anterior é criada com o comando CREATE TABLE. Cada coluna recebe um nome e um tipo de dado, e pode ter restrições (constraints).

criar_tabela.sql
CREATE TABLE tb_usuarios (
    id_usuario SERIAL PRIMARY KEY,
    tx_nome VARCHAR(100) NOT NULL,
    tx_email VARCHAR(150) UNIQUE NOT NULL,
    nr_idade INTEGER CHECK (nr_idade >= 0),
    dt_criacao TIMESTAMP DEFAULT NOW()
);
✓ CREATE TABLE — tabela "tb_usuarios" criada com sucesso.

Boas práticas para nomear tabelas e colunas

📛 Prefixo + minúsculo, sempre

Tabelas levam tb_: tb_usuarios, tb_pedidos — nunca Usuario ou USUARIOS.

🔤 Um prefixo, um significado

O prefixo já entrega o tipo do dado: dt_nascimento deixa claro que é uma data, sem precisar consultar a tabela.

🎯 Nomes claros, sem abreviar demais

Prefira vl_total a algo como vl_tot — quem lê a query depois agradece.

🔑 Chave estrangeira = cd_ + tabela referenciada

Em tb_pedidos, a coluna que aponta para tb_usuarios chama-se cd_usuario.

🚫 Evite palavras reservadas

Não nomeie colunas como order, table ou user — são palavras-chave do SQL.

🧭 Consistência acima de tudo

Se o padrão do projeto usa dt_criacao, use sempre dt_criacao — nunca misture com dt_criado em outra tabela.

Chave primária e chave estrangeira

A chave primária (PRIMARY KEY) identifica de forma única cada linha de uma tabela — nenhuma outra linha pode ter o mesmo valor. A chave estrangeira (FOREIGN KEY) é uma coluna que aponta para a chave primária de outra tabela, criando um relacionamento entre elas.

chave_estrangeira.sql
CREATE TABLE tb_pedidos (
    id_pedido SERIAL PRIMARY KEY,
    cd_usuario INTEGER REFERENCES tb_usuarios(id_usuario),
    vl_total NUMERIC(10,2) NOT NULL
);
✓ CREATE TABLE — "tb_pedidos" criada; cd_usuario só aceita ids que existam em "tb_usuarios".
💡
A FOREIGN KEY garante integridade referencial: não é possível inserir um pedido com cd_usuario que não exista na tabela tb_usuarios, nem apagar um usuário que ainda tenha pedidos vinculados (a menos que isso seja configurado explicitamente).

O que é o SERIAL

SERIAL não é bem um tipo de dado — é um "atalho" do PostgreSQL que cria uma coluna INTEGER, gera uma SEQUENCE por trás dos panos e configura essa sequência como valor padrão da coluna. Na prática, cada novo INSERT recebe automaticamente o próximo número — ideal para colunas id_.

NOT NULL, UNIQUE, CHECK e DEFAULT

Além das chaves, essas constraints (restrições) protegem a qualidade dos dados diretamente na definição da coluna:

🚧 NOT NULL

Obriga o preenchimento da coluna — não permite salvar a linha sem esse valor.

🎫 UNIQUE

Impede que dois registros tenham o mesmo valor nessa coluna, como um e-mail duplicado.

✅ CHECK

Valida uma regra de negócio antes de gravar, como nr_idade >= 0.

🧩 DEFAULT

Define um valor automático quando nenhum é informado, como DEFAULT NOW().

Uma segunda forma: criando a tabela "por extenso"

Até aqui, as constraints foram escritas inline, coladas na coluna. Existe uma segunda forma, mais extensa: declarar as colunas "limpas" e, no final do CREATE TABLE, listar cada constraint separadamente com um nome próprio (CONSTRAINT nome_da_regra ...). Fica mais longo, mas deixa cada regra fácil de identificar, alterar ou remover depois — e um índice pode ser criado logo em seguida, já pensando em performance.

criar_tabela_extensa.sql
CREATE TABLE tb_pedidos (
    id_pedido SERIAL,
    cd_usuario INTEGER,
    vl_total NUMERIC(10,2),
    tx_status VARCHAR(20) DEFAULT 'pendente',
    dt_criacao TIMESTAMP DEFAULT NOW(),

    CONSTRAINT pk_tb_pedidos PRIMARY KEY (id_pedido),
    CONSTRAINT fk_tb_pedidos_cd_usuario FOREIGN KEY (cd_usuario) REFERENCES tb_usuarios(id_usuario),
    CONSTRAINT ck_tb_pedidos_vl_total CHECK (vl_total >= 0),
    CONSTRAINT uq_tb_pedidos_cd_usuario_dt UNIQUE (cd_usuario, dt_criacao)
);

-- índice criado logo depois, para acelerar buscas por usuário
CREATE INDEX idx_tb_pedidos_cd_usuario ON tb_pedidos(cd_usuario);
✓ CREATE TABLE + CREATE INDEX — "tb_pedidos" criada com todas as regras nomeadas.
💡
Dar um nome à constraint (pk_tb_pedidos, fk_tb_pedidos_cd_usuario...) faz o PostgreSQL usar esse nome nas mensagens de erro — muito mais fácil de identificar o problema do que um nome genérico gerado automaticamente. Também facilita usar ALTER TABLE ... DROP CONSTRAINT nome depois.

DDL, DML e DCL

O SQL é dividido em sub-linguagens de acordo com o que o comando faz:

DDL

Data Definition Language

Define e altera a estrutura: CREATE, ALTER, DROP, TRUNCATE.

DML

Data Manipulation Language

Manipula os dados dentro das tabelas: SELECT, INSERT, UPDATE, DELETE.

DCL

Data Control Language

Controla permissões de acesso: GRANT, REVOKE.

➕
Bônus — TCL (Transaction Control Language): BEGIN, COMMIT e ROLLBACK controlam transações, agrupando vários comandos como uma única operação tudo-ou-nada.

DCL na prática: permissões e acesso

O DCL (Data Control Language) é a parte do SQL que decide quem pode fazer o quê no banco — quem lê, quem grava, quem apaga, quem pode até criar novas tabelas. Sem ele, todo mundo que se conecta ao banco teria acesso total a tudo.

Por que usar DCL

🔒 Princípio do menor privilégio

Cada usuário ou aplicação recebe só o acesso necessário para o seu trabalho — nada mais.

🛑 Evita desastres

Uma aplicação de leitura não deveria conseguir rodar um DELETE por engano ou por uma falha de segurança.

🧾 Auditoria e organização

Fica claro quem tem acesso a quê — essencial em times grandes e em dados sensíveis.

Todos os comandos

GRANT

Conceder privilégio

Dá a uma role/usuário permissão para executar uma ação sobre um objeto do banco.

REVOKE

Revogar privilégio

Remove uma permissão concedida anteriormente.

CREATE ROLE

Criar uma role

Cria um usuário ou grupo de permissões (no PostgreSQL, usuários são roles).

ALTER ROLE

Alterar uma role

Muda senha, validade ou características de uma role já existente.

DROP ROLE

Remover uma role

Apaga a role — só funciona se ela não tiver mais nenhum privilégio pendente.

Como criar uma role e conceder acesso

criar_role.sql
-- cria uma role com login e senha (na prática, um "usuário")
CREATE ROLE app_leitura WITH LOGIN PASSWORD 'senha_segura';
✓ CREATE ROLE — "app_leitura" criada.
grant.sql
-- concede permissão só de leitura em uma tabela específica
GRANT SELECT ON tb_usuarios TO app_leitura;

-- concede várias permissões de uma vez
GRANT SELECT, INSERT, UPDATE ON tb_pedidos TO app_leitura;

-- concede em todas as tabelas de um schema
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_leitura;
✓ GRANT — privilégios concedidos a "app_leitura".
revoke.sql
-- remove a permissão de inserir, mantendo a de ler
REVOKE INSERT ON tb_pedidos FROM app_leitura;
✓ REVOKE — privilégio removido de "app_leitura".

Como configurar: roles de grupo e privilégios padrão

Em vez de conceder permissões usuário por usuário, é comum criar uma role de grupo com os privilégios certos e depois adicionar usuários a ela.

role_de_grupo.sql
-- role "sem login", usada só como grupo de permissões
CREATE ROLE grupo_financeiro WITH NOLOGIN;
GRANT SELECT, INSERT, UPDATE ON tb_pedidos TO grupo_financeiro;

-- adiciona um usuário real ao grupo
GRANT grupo_financeiro TO app_leitura;
✓ "app_leitura" herdou os privilégios de "grupo_financeiro".
privilegios_padrao.sql
-- aplica automaticamente em toda tabela criada depois disso
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT ON TABLES TO app_leitura;
✓ ALTER DEFAULT PRIVILEGES — próximas tabelas já nascem visíveis para "app_leitura".
⚙️
O DCL controla o acesso dentro do banco (o que uma role pode fazer nos dados). Já a permissão de conexão ao servidor (de qual IP, com qual método de autenticação) é configurada fora do SQL, no arquivo pg_hba.conf do PostgreSQL.

SELECT — consultando dados

O SELECT é o comando mais usado do SQL: busca linhas de uma ou mais tabelas. O PostgreSQL primeiro localiza e filtra as linhas (FROM / WHERE), depois ordena e limita o resultado.

select.sql
SELECT tx_nome, tx_email
FROM tb_usuarios
WHERE nr_idade >= 18
ORDER BY tx_nome ASC
LIMIT 10;

UPDATE — alterando dados

Atualiza valores de uma ou mais linhas existentes. Sempre use o WHERE — sem ele, todas as linhas da tabela são alteradas.

update.sql
UPDATE tb_usuarios
SET nr_idade = 29
WHERE tx_email = 'ana@email.com';
✓ UPDATE 1 — 1 linha atualizada.

DELETE — removendo dados

Remove linhas da tabela. Assim como o UPDATE, exige atenção redobrada com o WHERE.

delete.sql
DELETE FROM tb_usuarios
WHERE id_usuario = 5;
✓ DELETE 1 — 1 linha removida.

ALTER TABLE — mudando a estrutura

Modifica a estrutura de uma tabela já existente, sem precisar recriá-la.

alter.sql
ALTER TABLE tb_usuarios ADD COLUMN tx_telefone VARCHAR(20);
ALTER TABLE tb_usuarios DROP COLUMN nr_idade;
ALTER TABLE tb_usuarios ALTER COLUMN tx_nome TYPE VARCHAR(200);
ALTER TABLE tb_usuarios RENAME COLUMN tx_email TO tx_email_contato;
✓ ALTER TABLE — estrutura atualizada.

GROUP BY, HAVING, COUNT e SUM

GROUP BY agrupa linhas que compartilham o mesmo valor em uma coluna, para então aplicar funções de agregação como COUNT (conta linhas) e SUM (soma valores) em cada grupo. O HAVING filtra os grupos já formados — diferente do WHERE, que filtra linhas individuais antes de agrupar.

group_by.sql
SELECT cd_usuario,
       COUNT(*) AS nr_total_pedidos,
       SUM(vl_total) AS vl_total_gasto
FROM tb_pedidos
GROUP BY cd_usuario
HAVING SUM(vl_total) > 500;

32640.00
💡
WHERE filtra linhas antes de agrupar; HAVING filtra os grupos depois de agrupar — por isso é o único lugar onde faz sentido usar SUM() ou COUNT() dentro de uma condição.

INNER, LEFT e RIGHT JOIN

Um JOIN combina linhas de duas tabelas com base em uma condição — normalmente comparando uma chave estrangeira com a chave primária correspondente.

INNER JOIN

Só as linhas que casam nas duas tabelas.

LEFT JOIN

Todas as linhas da esquerda + as que casam à direita.

RIGHT JOIN

Todas as linhas da direita + as que casam à esquerda.

inner_join.sql
SELECT p.id_pedido, u.tx_nome, p.vl_total
FROM tb_pedidos p
INNER JOIN tb_usuarios u ON p.cd_usuario = u.id_usuario;
✓ retorna só os pedidos que têm um usuário correspondente.
left_join.sql
SELECT u.tx_nome, p.id_pedido
FROM tb_usuarios u
LEFT JOIN tb_pedidos p ON p.cd_usuario = u.id_usuario;
✓ traz todos os usuários, com NULL em "id_pedido" para quem não tem pedido.
right_join.sql
SELECT u.tx_nome, p.id_pedido
FROM tb_usuarios u
RIGHT JOIN tb_pedidos p ON p.cd_usuario = u.id_usuario;
✓ traz todos os pedidos, com NULL em "tx_nome" se o usuário não existir.

Para juntar textos, use o operador || ou a função CONCAT() — as duas formas fazem a mesma coisa.

WITH (CTE) e subqueries

Consultas complexas ficam mais fáceis de escrever e de ler quando são divididas em partes menores. É para isso que servem o WITH e as subqueries.

WITH — Common Table Expression (CTE)

O WITH cria uma "tabela temporária" nomeada, que existe só durante aquela consulta. Ajuda a dividir uma query grande em passos nomeados, em vez de aninhar subqueries difíceis de ler.

with.sql
WITH pedidos_recentes AS (
    SELECT *
    FROM tb_pedidos
    WHERE dt_criacao >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT cd_usuario, COUNT(*) AS nr_total
FROM pedidos_recentes
GROUP BY cd_usuario;

Subquery — consulta dentro de consulta

Uma subquery é um SELECT usado dentro de outro comando — como valor de comparação, lista de valores ou até como se fosse uma tabela.

subquery_valor.sql
-- usuários mais velhos que a média de idade
SELECT tx_nome, nr_idade
FROM tb_usuarios
WHERE nr_idade > (SELECT AVG(nr_idade) FROM tb_usuarios);

subquery_tabela.sql
-- subquery usada como se fosse uma tabela (derived table)
SELECT * FROM (
    SELECT cd_usuario, SUM(vl_total) AS vl_total
    FROM tb_pedidos
    GROUP BY cd_usuario
) AS resumo
WHERE vl_total > 500;

EXISTS e NOT EXISTS

EXISTS testa se uma subquery retorna pelo menos uma linha — o resultado é apenas verdadeiro ou falso, sem importar quais valores vieram. Costuma ser mais eficiente que comparar com IN, porque o PostgreSQL para de procurar assim que encontra a primeira linha.

exists.sql
-- usuários que têm pelo menos um pedido
SELECT tx_nome
FROM tb_usuarios u
WHERE EXISTS (
    SELECT 1 FROM tb_pedidos p WHERE p.cd_usuario = u.id_usuario
);
tx_nome

not_exists.sql
-- usuários que nunca fizeram nenhum pedido
SELECT tx_nome
FROM tb_usuarios u
WHERE NOT EXISTS (
    SELECT 1 FROM tb_pedidos p WHERE p.cd_usuario = u.id_usuario
);

Dentro de um EXISTS não importa o que vem depois do SELECT — por convenção usa-se SELECT 1, já que só a existência da linha importa, não seu conteúdo.

VIEW — consultas salvas

Uma view é uma consulta SQL salva com um nome, que se comporta como uma tabela virtual — sem duplicar os dados. Toda vez que a view é consultada, a query original roda por trás.

view.sql
CREATE VIEW vw_usuarios_ativos AS
SELECT id_usuario, tx_nome, tx_email
FROM tb_usuarios
WHERE fl_ativo = true;
✓ CREATE VIEW — "vw_usuarios_ativos" pronta para uso como SELECT * FROM vw_usuarios_ativos;

INDEX — acelerando buscas

Um índice é uma estrutura auxiliar que acelera buscas, funcionando como o índice remissivo de um livro. Acelera leituras, mas tem custo em espaço e em escrita (cada INSERT/UPDATE também atualiza o índice).

index.sql
CREATE INDEX idx_tb_usuarios_tx_email ON tb_usuarios(tx_email);
✓ CREATE INDEX — buscas por "email" ficam muito mais rápidas.

EXPLAIN ANALYZE — o raio-x da query

Mostra o plano de execução real usado pelo PostgreSQL: se ele varreu a tabela inteira (Seq Scan) ou usou um índice (Index Scan), quanto tempo levou e quantas linhas encontrou. Essencial para diagnosticar queries lentas.

explain.sql
EXPLAIN ANALYZE
SELECT * FROM tb_usuarios WHERE tx_email = 'ana@email.com';
Index Scan using idx_tb_usuarios_tx_email on tb_usuarios (cost=0.28..8.30 rows=1 width=64) (actual time=0.02..0.03 rows=1 loops=1) Planning Time: 0.08 ms · Execution Time: 0.04 ms

SEQUENCE — geradores de número

Uma sequence gera números sequenciais únicos. É exatamente o mecanismo que o tipo SERIAL usa por trás dos panos para criar IDs automáticos.

sequence.sql
CREATE SEQUENCE sq_pedido_id START 1000 INCREMENT 1;
SELECT nextval('sq_pedido_id');
nextval
1000

FUNCTION — código reutilizável

Uma function é um bloco de lógica reutilizável dentro do banco: recebe parâmetros, executa comandos e pode retornar um valor. É o que a trigger acima está chamando.

function.sql
CREATE FUNCTION fn_atualizar_timestamp()
RETURNS TRIGGER AS $$
BEGIN
    NEW.dt_criacao = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
✓ CREATE FUNCTION — "fn_atualizar_timestamp" disponível para uso.

TRIGGER — reações automáticas

Uma trigger executa uma função automaticamente antes ou depois de um evento (INSERT, UPDATE ou DELETE) acontecer em uma tabela.

trigger.sql
CREATE TRIGGER trg_atualiza_data
BEFORE UPDATE ON tb_usuarios
FOR EACH ROW
EXECUTE FUNCTION fn_atualizar_timestamp();
✓ CREATE TRIGGER — a cada UPDATE, a função é disparada automaticamente.

VACUUM — limpeza e manutenção

O PostgreSQL usa MVCC (controle de concorrência multiversão): ao fazer UPDATE ou DELETE, a linha antiga não é apagada na hora, fica marcada como "morta". O VACUUM libera esse espaço e atualiza estatísticas que o otimizador usa para montar planos de execução.

Tipos de VACUUM

🧹 VACUUM (padrão)

Marca o espaço das linhas mortas como reutilizável pela própria tabela, mas não devolve o espaço para o sistema operacional. Não bloqueia leituras nem escritas — pode rodar com a tabela em uso.

🗜️ VACUUM FULL

Reescreve a tabela inteira do zero, compactando tudo e devolvendo o espaço para o sistema operacional. É mais eficiente em espaço, porém mais lento e bloqueia a tabela (leituras e escritas) durante a execução.

📊 VACUUM ANALYZE

Faz o VACUUM padrão e, em seguida, atualiza as estatísticas da tabela — as mesmas que o planejador de consultas usa para decidir entre um Seq Scan ou um Index Scan.

📈 ANALYZE

Só atualiza as estatísticas, sem liberar espaço nenhum. Útil quando os dados mudaram bastante mas não há muitas linhas mortas para limpar.

🧊 VACUUM FREEZE

Força o "congelamento" de linhas antigas para evitar o problema de transaction ID wraparound — importante em tabelas grandes e pouco alteradas.

🤖 Autovacuum

Processo em segundo plano, ativado por padrão, que roda VACUUM e ANALYZE automaticamente quando uma tabela acumula mudanças suficientes — na prática, é o que cuida da manutenção do dia a dia.

vacuum.sql
VACUUM ANALYZE tb_usuarios;
✓ VACUUM — espaço morto liberado e estatísticas atualizadas.
⚠️
VACUUM FULL reescreve a tabela inteira do zero: libera mais espaço, mas é mais lento e bloqueia a tabela durante a execução — use com cuidado em produção. No dia a dia, o autovacuum já resolve a maior parte dos casos sem intervenção manual.

Backup e restauração

Um backup é uma cópia de segurança dos dados, feita para recuperar o banco em caso de falha de hardware, erro humano (um DELETE sem WHERE, por exemplo), corrupção de dados ou qualquer desastre. Sem backup, um problema desses pode significar perda definitiva de informação.

psql é o cliente de linha de comando oficial do PostgreSQL — é por ele que você se conecta a um banco direto pelo terminal, executa comandos SQL de forma interativa e roda tarefas administrativas, incluindo restaurar arquivos .sql. Ele acompanha a instalação do PostgreSQL e é a ferramenta mais direta para falar com o banco sem depender de uma interface gráfica.

🛡️ pg_dump

Gera o backup lógico de um único banco de dados — as tabelas, dados, views, functions etc.

🗄️ pg_dumpall

Faz backup de todos os bancos do servidor, incluindo roles (usuários) e permissões globais.

♻️ pg_restore / psql

Restauram um backup gerado pelo pg_dump, recriando estrutura e dados.

Como criar um backup

O pg_dump é executado no terminal (fora do psql). Ele aceita dois formatos principais: plain (um arquivo .sql legível) ou custom (binário, comprimido, mais rápido e flexível na hora de restaurar).

terminal — backup em formato .sql (plain)
# gera um arquivo .sql legível com toda a estrutura e os dados
pg_dump -U postgres -d minha_base -f backup.sql
✓ backup.sql gerado com sucesso.
terminal — backup em formato custom (recomendado)
# -F c = formato custom (compactado, permite restauração seletiva)
pg_dump -U postgres -d minha_base -F c -f backup.dump
✓ backup.dump gerado com sucesso.
terminal — backup de todos os bancos do servidor
# inclui todos os bancos + roles/usuários do cluster
pg_dumpall -U postgres -f backup_completo.sql
✓ backup_completo.sql gerado com sucesso.

Como restaurar um backup

A ferramenta usada para restaurar depende do formato do backup: arquivos .sql são executados com psql; arquivos .dump (custom) são restaurados com pg_restore.

terminal — restaurar um backup .sql
# o banco de destino já precisa existir
psql -U postgres -d minha_base_nova -f backup.sql
✓ dados restaurados em "minha_base_nova".
terminal — restaurar um backup .dump (custom)
# --clean remove os objetos existentes antes de recriá-los
pg_restore -U postgres -d minha_base_nova --clean backup.dump
✓ dados restaurados em "minha_base_nova".
💡
Boas práticas: agende backups automáticos, teste a restauração periodicamente (um backup nunca testado é um backup que você não sabe se funciona) e guarde as cópias em um local diferente do servidor original.
