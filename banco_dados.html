O que é um banco de dados?

Um banco de dados é um conjunto organizado de dados, guardado de forma estruturada para que possam ser armazenados, consultados, alterados e apagados de maneira confiável — sem depender de arquivos soltos como planilhas ou textos.

📦 Organização

Os dados ficam em estruturas previsíveis (tabelas), não em arquivos avulsos.

🔒 Confiabilidade

Regras garantem que os dados fiquem consistentes mesmo com vários acessos simultâneos.

🔍 Consulta

É possível buscar, filtrar e cruzar informações rapidamente usando SQL.

💡
Analogia: pense num arquivo de gavetas de um escritório, só que digital — cada gaveta é organizada por categoria, tem etiquetas e um sistema que sabe exatamente onde cada papel está.

O que é um SGBD?

SGBD (Sistema Gerenciador de Banco de Dados) é o software que fica entre você (ou sua aplicação) e os dados guardados fisicamente no disco. Você nunca mexe nos dados diretamente — sempre pede ao SGBD que faça isso.

Armazenamento

Organiza fisicamente onde e como os dados ficam salvos no disco.

Controle de acesso

Define quem pode ler, escrever ou apagar cada informação.

Integridade

Garante regras como "e-mail não pode se repetir".

Concorrência

Permite vários usuários acessando ao mesmo tempo sem corromper dados.

Exemplos de SGBD: PostgreSQL, MySQL, SQL Server, Oracle, SQLite. Este guia usa o PostgreSQL — relacional, open-source e amplamente adotado no mercado.

Diagrama Entidade-Relacionamento (DER)

Antes de criar a primeira tabela, planeje o banco: um DER representa as entidades (futuras tabelas), seus atributos (colunas) e como elas se relacionam — tudo sem escrever uma linha de SQL.

🧩 O que ele mostra

Entidades, atributos principais, chave primária de cada uma e os relacionamentos com cardinalidade.

🎯 Por que é importante

Planejar no papel é mais barato que corrigir em produção. Evita retrabalho e serve de documentação.

🗣️ Facilita comunicação

É a linguagem comum entre quem programa e quem entende o negócio — valida regras antes de implementar.

Como criar um DER

  1. Identifique as entidades — os "substantivos" do sistema: usuário, pedido, produto…
  2. Liste os atributos de cada entidade — o que precisa ser guardado sobre ela.
  3. Defina a chave primária — o que identifica cada registro de forma única.
  4. Trace os relacionamentos e defina a cardinalidade de cada um.
  5. Desenhe — no papel ou em ferramentas como draw.io, dbdiagram.io, brModelo ou pgAdmin.

Cardinalidades

Um para um (1:1)

1 usuário tem no máximo 1 perfil, e vice-versa. FK recebe UNIQUE.

Um para muitos (1:N)

1 usuário tem vários pedidos; cada pedido pertence a 1 usuário. FK fica na tabela "muitos".

Muitos para muitos (N:N)

Vários pedidos têm vários produtos. Exige tabela associativa no meio.

n_para_n.sql — tabela associativa
CREATE TABLE tb_itens_pedido (
    cd_pedido INTEGER REFERENCES tb_pedidos(id_pedido),
    cd_produto INTEGER REFERENCES tb_produtos(id_produto),
    nr_quantidade INTEGER NOT NULL,
    PRIMARY KEY (cd_pedido, cd_produto)
);
✓ "tb_itens_pedido" liga tb_pedidos e tb_produtos — uma linha por combinação.

Tipos de dados

Cada coluna precisa de um tipo, que define que tipo de valor ela aceita e quanto espaço ocupa no disco.

TipoUso

Boas práticas: nomes com prefixo

Muitas empresas adotam um prefixo de 2 letras no nome de cada coluna, indicando o tipo de dado que ela guarda. Tudo sempre em minúsculo. O significado fica visível só de olhar o nome — sem abrir a estrutura da tabela.

💡
A regra de ouro é a consistência: escolhido o padrão, ele precisa valer para todas as tabelas do banco — sempre minúsculo, sempre o mesmo prefixo para o mesmo tipo de dado, do início ao fim do projeto.

Como criar uma tabela

A tabela é criada com CREATE TABLE. Cada coluna recebe um nome e um tipo de dado, e pode ter restrições (constraints).

criar_tabela.sql
CREATE TABLE tb_usuarios (
    id_usuario SERIAL PRIMARY KEY,
    tx_nome    VARCHAR(100) NOT NULL,
    tx_email   VARCHAR(150) UNIQUE NOT NULL,
    nr_idade   INTEGER      CHECK (nr_idade >= 0),
    fl_ativo   BOOLEAN      DEFAULT true,
    dt_criacao TIMESTAMP   DEFAULT NOW()
);
✓ CREATE TABLE — "tb_usuarios" criada com sucesso.

Constraints (restrições)

🚧 NOT NULL

Obriga o preenchimento — não permite salvar a linha sem esse valor.

🎫 UNIQUE

Impede duplicatas na coluna, como e-mails repetidos.

✅ CHECK

Valida uma regra de negócio antes de gravar: nr_idade >= 0.

🧩 DEFAULT

Define valor automático quando nenhum é informado: DEFAULT NOW().

Chave primária e chave estrangeira

A PRIMARY KEY identifica unicamente cada linha. A FOREIGN KEY aponta para a chave primária de outra tabela, criando um relacionamento — o banco rejeita inserções que violem essa relação.

chave_estrangeira.sql
CREATE TABLE tb_pedidos (
    id_pedido  SERIAL      PRIMARY KEY,
    cd_usuario INTEGER     REFERENCES tb_usuarios(id_usuario),
    vl_total   NUMERIC(10,2) NOT NULL
);
✓ "tb_pedidos" criada; cd_usuario só aceita ids que existam em tb_usuarios.

DDL, DML e DCL

O SQL é dividido em sub-linguagens de acordo com o que o comando faz:

DDL

Data Definition Language

Define e altera a estrutura: CREATE, ALTER, DROP, TRUNCATE.

DML

Data Manipulation Language

Manipula os dados dentro das tabelas: SELECT, INSERT, UPDATE, DELETE.

DCL

Data Control Language

Controla permissões: GRANT, REVOKE, CREATE ROLE.

➕
TCL (Transaction Control Language): BEGIN, COMMIT e ROLLBACK agrupam vários comandos como uma única operação tudo-ou-nada.

DCL na prática: permissões e acesso

O DCL decide quem pode fazer o quê no banco. Sem ele, todo usuário conectado teria acesso total a tudo.

DELETERemover linhas.
TRUNCATEEsvaziar a tabela inteira de uma vez.

ALL PRIVILEGESConcede (ou revoga) todos os privilégios de uma vez.
dcl.sql — criar role e conceder acesso
CREATE ROLE app_leitura WITH LOGIN PASSWORD 'senha_segura';

GRANT SELECT ON tb_usuarios TO app_leitura;
GRANT SELECT, INSERT, UPDATE ON tb_pedidos TO app_leitura;

-- revogar um privilégio específico
REVOKE INSERT ON tb_pedidos FROM app_leitura;
✓ Role criada, permissões concedidas e revogadas com sucesso.

Insere uma nova linha na tabela. As colunas e valores precisam estar na mesma ordem.

  ('Bruno Costa', 'bruno@email.com', 34),
  ('Carla Dias',  'carla@email.com',  21);

SELECT — consultando dados

O SELECT é o comando mais usado do SQL. O PostgreSQL primeiro localiza e filtra as linhas (FROM / WHERE), depois agrupa, ordena e limita o resultado.

select.sql
SELECT tx_nome, tx_email
FROM   tb_usuarios
WHERE  nr_idade >= 18
ORDER BY tx_nome ASC
LIMIT  10;

Ordem de execução lógica

1 · FROM

Define de qual tabela os dados vêm.

2 · WHERE

Filtra as linhas antes de qualquer agrupamento.

3 · GROUP BY

Agrupa linhas por valor de coluna.

4 · HAVING

Filtra os grupos já formados.

5 · SELECT

Define quais colunas aparecem no resultado.

6 · ORDER BY + LIMIT

Ordena e limita o conjunto final.

💡
O SELECT aparece primeiro quando você escreve a query, mas é executado depois do WHERE e do GROUP BY. Por isso você não pode usar um alias do SELECT dentro do WHERE — o alias ainda não existe naquele momento de execução.

UPDATE — alterando dados

      
Atualiza valores de uma ou mais linhas existentes. Sempre use o WHERE — sem ele, todas as linhas da tabela são alteradas.

      

        
update.sql

        
UPDATE tb_usuarios
SET    nr_idade = 29
WHERE  tx_email = 'ana@email.com';

        
✓ UPDATE 1 — 1 linha atualizada.

      

      
⚠️
Um UPDATE sem WHERE altera todas as linhas da tabela — sem aviso e sem desfazer. Antes de rodar um UPDATE em produção, teste primeiro com um SELECT usando o mesmo WHERE.

    


    
    

      
DELETE — removendo dados

      
Remove linhas da tabela. Assim como o UPDATE, exige atenção redobrada com o WHERE.

      

        
delete.sql

        
DELETE FROM tb_usuarios
WHERE id_usuario = 5;

        
✓ DELETE 1 — 1 linha removida.

Filtros essenciais no WHERE

      
O WHERE filtra linhas antes de qualquer agrupamento ou ordenação. Além dos operadores básicos (=, <>, >, <), o PostgreSQL oferece operadores de alto nível que tornam as consultas mais legíveis e expressivas.


      
      
BETWEEN — intervalo inclusivo

      
BETWEEN x AND y é equivalente a >= x AND <= y — ambas as bordas estão incluídas. Funciona com números, datas e textos. Existe também NOT BETWEEN para excluir o intervalo.

      

        
between.sql — faixa numérica e de datas

        
-- idades entre 18 e 30 (18 e 30 incluídos)
SELECT tx_nome, nr_idade
FROM   tb_usuarios
WHERE  nr_idade BETWEEN 18 AND 30;

-- pedidos em janeiro de 2026
SELECT id_pedido, vl_total
FROM   tb_pedidos
WHERE  dt_criacao BETWEEN '2026-01-01' AND '2026-01-31 23:59:59';

        
tx_nomenr_idade

Carla Dias21

        

      

      
⚠️
Com datas+hora (TIMESTAMP), termine o intervalo em '2026-01-31 23:59:59' ou use dt_criacao < '2026-02-01' — caso contrário, pedidos das 23:59 do último dia ficam fora.


      
      
IN / NOT IN — lista de valores

      
IN filtra linhas cujo valor coincida com qualquer item de uma lista — substitui vários OR encadeados. A lista pode ser literal ou uma subquery. NOT IN faz o inverso, mas atenção: se a lista contiver um NULL, o NOT IN nunca retorna nada (comportamento do padrão SQL — prefira NOT EXISTS nesses casos).

      

        
in.sql — lista estática e com subquery

        
-- lista estática
SELECT tx_nome, tx_cidade
FROM   tb_usuarios
WHERE  tx_cidade IN ('Florianópolis', 'Chapecó', 'Joinville');

-- lista gerada por subquery
SELECT id_pedido, vl_total
FROM   tb_pedidos
WHERE  cd_usuario IN (
    SELECT id_usuario FROM tb_usuarios WHERE fl_ativo = true
);

        
✓ IN aceita tanto uma lista literal quanto o resultado de outra query.

      


      
      
LIKE e ILIKE — busca por padrão de texto

      
LIKE compara textos usando curingas: % substitui qualquer sequência de caracteres e _ substitui exatamente um caractere. ILIKE é a versão case-insensitive exclusiva do PostgreSQL.

      

        
'Ana%'
Começa com "Ana" — qualquer coisa depois.

        
'%Silva'
Termina com "Silva" — qualquer coisa antes.

        
'%silva%'
Contém "silva" em qualquer posição.

      

      

        
like.sql

        
-- nomes que começam com "Ana" (sensível a maiúscula)
SELECT tx_nome FROM tb_usuarios WHERE tx_nome LIKE 'Ana%';

-- ILIKE: ignora maiúsculas/minúsculas
SELECT tx_nome FROM tb_usuarios WHERE tx_nome ILIKE '%silva%';

-- e-mails de domínio gmail
SELECT tx_nome, tx_email FROM tb_usuarios
WHERE  tx_email LIKE '%@gmail.com';

        
tx_nome

          
Ana Silva
Ana Beatriz

        

      

      
⚠️
Padrões que começam com % (ex: LIKE '%texto') forçam varredura total da tabela — o índice não pode ser aproveitado. Prefira LIKE 'texto%' quando possível, ou use a extensão pg_trgm para busca textual avançada com índice.


      
      
UPPER e LOWER — normalizar capitalização

      
UPPER() converte para maiúsculas e LOWER() para minúsculas. Use para padronizar comparações — assim "ana", "Ana" e "ANA" tornam-se equivalentes.

      

        
upper_lower.sql

        
-- busca sem distinguir maiúsculas/minúsculas
SELECT tx_nome
FROM   tb_usuarios
WHERE  LOWER(tx_nome) = LOWER('ANA SILVA');

-- exibir formatado: nome em maiúsculo, e-mail em minúsculo
SELECT
    UPPER(tx_nome)  AS tx_nome_exibicao,
    LOWER(tx_email) AS tx_email_normalizado
FROM tb_usuarios;

ORDER BY ASC e DESC — ordenar resultados

      
ORDER BY define a ordem das linhas no resultado. ASC (crescente) é o padrão e pode ser omitido; DESC (decrescente) precisa ser declarado. É possível ordenar por múltiplas colunas — o critério seguinte só entra em ação quando o anterior empata.

      

        
order_by.sql

        
-- mais recente primeiro; empate na data → maior valor primeiro
SELECT id_pedido, dt_criacao, vl_total
FROM   tb_pedidos
ORDER BY dt_criacao DESC, vl_total DESC;

CASE WHEN — lógica condicional

      
CASE WHEN é o if/else do SQL: avalia condições em sequência e retorna o valor do primeiro WHEN verdadeiro. Pode ser usado em qualquer parte do SELECT — inclusive dentro de funções de agregação.

      

        
case_when.sql — categorizar e contar por status

        
-- classificar faixa etária
SELECT
    tx_nome, nr_idade,
    CASE
        WHEN nr_idade < 18  THEN 'Menor de idade'
        WHEN nr_idade <= 30 THEN 'Jovem adulto'
        WHEN nr_idade <= 60 THEN 'Adulto'
        ELSE                      'Sênior'
    END AS tx_faixa_etaria
FROM tb_usuarios;

-- CASE WHEN dentro de COUNT — contar por status
SELECT
    COUNT(CASE WHEN fl_ativo = true  THEN 1 END) AS nr_ativos,
    COUNT(CASE WHEN fl_ativo = false THEN 1 END) AS nr_inativos
FROM tb_usuarios;

Funções de agregação: COUNT, SUM, AVG, MIN e MAX

      
Funções de agregação operam sobre um conjunto de linhas e retornam um único valor resumido. Elas são sempre usadas junto com GROUP BY (para resumir por categoria) ou sozinhas (para resumir toda a tabela). Todas ignoram valores NULL, exceto COUNT(*).

            Conta todas as linhas do grupo, incluindo NULLs.
            Não
          

          

            COUNT(coluna)
            Conta linhas onde a coluna não é NULL.
            Sim
          

          

            COUNT(DISTINCT col)
            Conta valores únicos na coluna, sem repetição.
            Sim
          

          

            SUM(coluna)
            Soma os valores numéricos da coluna.
            Sim
          

          

            AVG(coluna)
            Calcula a média aritmética dos valores numéricos.
            Sim
          

          

            MIN(coluna)
            Retorna o menor valor — funciona com números, datas e textos.
            Sim
          

          

            MAX(coluna)
            Retorna o maior valor — funciona com números, datas e textos.
            Sim

-- estatísticas gerais dos pedidos
SELECT
    COUNT(*)                    AS nr_total_pedidos,
    COUNT(DISTINCT cd_usuario)  AS nr_clientes_unicos,
    SUM(vl_total)               AS vl_receita_total,
    AVG(vl_total)               AS vl_ticket_medio,
    MIN(vl_total)               AS vl_menor_pedido,
    MAX(vl_total)               AS vl_maior_pedido
FROM tb_pedidos;

GROUP BY — agrupar para agregar

      
GROUP BY divide as linhas em grupos com o mesmo valor em uma ou mais colunas e aplica uma função de agregação em cada grupo separadamente. Toda coluna no SELECT que não estiver dentro de uma função de agregação obrigatoriamente precisa aparecer no GROUP BY.

      

        
group_by.sql — total por usuário

        
SELECT
    cd_usuario,
    COUNT(*)       AS nr_pedidos,
    SUM(vl_total)  AS vl_total_gasto,
    AVG(vl_total)  AS vl_medio,
    MIN(vl_total)  AS vl_menor,
    MAX(vl_total)  AS vl_maior
FROM  tb_pedidos
GROUP BY cd_usuario
ORDER BY vl_total_gasto DESC;

HAVING — filtrar grupos

      
HAVING filtra os grupos depois do agrupamento — ao contrário do WHERE, que filtra linhas antes. Por isso é o único lugar onde faz sentido usar funções de agregação (SUM, COUNT…) como condição.

      

        
WHERE
Filtra linhas individuais antes de agrupar. Não pode usar SUM(), COUNT() etc.

        
HAVING
Filtra grupos depois de agrupar. É aqui que se usa SUM(vl_total) > 500.

      

      

        
having.sql — usuários que gastaram mais de R$ 500

        
SELECT
    cd_usuario,
    COUNT(*) AS nr_pedidos,
    SUM(vl_total) AS vl_total_gasto
FROM  tb_pedidos
GROUP BY cd_usuario
HAVING SUM(vl_total) > 500    -- filtra grupos, não linhas
ORDER BY vl_total_gasto DESC;

JOINs — combinando tabelas

      
Um JOIN combina linhas de duas tabelas com base em uma condição — normalmente a chave estrangeira de uma igualada à chave primária da outra. A escolha do tipo de JOIN determina o que acontece quando não existe correspondência em um dos lados.


      

        

          
          INNER JOIN
          
Interseção

          
Só linhas que têm correspondência nas duas tabelas. Descarta quem não casa.

        

        

          
          LEFT JOIN
          
Tabela da esquerda completa

          
Todas as linhas da esquerda + correspondências da direita. Sem correspondência → NULL à direita.

        

        

          
          RIGHT JOIN
          
Tabela da direita completa

          
Todas as linhas da direita + correspondências da esquerda. Sem correspondência → NULL à esquerda.

        

        

          
          FULL OUTER JOIN
          
União completa

          
Todas as linhas dos dois lados. Sem correspondência de nenhum dos lados → NULL nos campos do outro.

        

      


      

        
inner_join.sql — só os que casam nos dois lados

        
-- retorna só os pedidos que têm um usuário existente
SELECT p.id_pedido, u.tx_nome, p.vl_total
FROM   tb_pedidos p
INNER JOIN tb_usuarios u ON p.cd_usuario = u.id_usuario;

WITH (CTE) e subqueries

      
Consultas complexas ficam mais fáceis de escrever e ler quando são divididas em partes menores. O WITH e as subqueries são as duas ferramentas para isso — complementares, não concorrentes.


      
      
WITH — Common Table Expression (CTE)

      
O WITH cria uma ou mais "tabelas temporárias" nomeadas que existem apenas durante aquela consulta. Cada bloco nomeado pode ser referenciado depois como se fosse uma tabela real. O objetivo é transformar uma query grande e aninhada em passos sequenciais com nomes descritivos.

      

        
✅ Use CTE quando…
A mesma subquery é usada mais de uma vez, ou quando a query tem mais de dois níveis de aninhamento e está difícil de ler.

        
⚡ Prefira subquery quando…
A lógica é simples, usada em um único lugar e aninhar não prejudica a leitura.

      

      

        
with_cte.sql — passo a passo legível

        
WITH
-- passo 1: pedidos dos últimos 30 dias
pedidos_recentes AS (
    SELECT *
    FROM  tb_pedidos
    WHERE dt_criacao >= CURRENT_DATE - INTERVAL '30 days'
),
-- passo 2: resumo por usuário usando o resultado acima
resumo_usuario AS (
    SELECT
        cd_usuario,
        COUNT(*) AS nr_pedidos,
        SUM(vl_total) AS vl_total
    FROM  pedidos_recentes
    GROUP BY cd_usuario
)
-- consulta final usa os dois CTEs
SELECT u.tx_nome, r.nr_pedidos, r.vl_total
FROM  resumo_usuario r
JOIN  tb_usuarios u ON u.id_usuario = r.cd_usuario
ORDER BY r.vl_total DESC;

Subquery — consulta dentro de consulta

      
Uma subquery é um SELECT aninhado dentro de outro comando. Pode aparecer como valor escalar (retorna 1 valor), lista de valores (no IN) ou como se fosse uma tabela (no FROM).

      

        
subquery.sql — valor escalar e tabela derivada

        
-- valor escalar: usuários mais velhos que a média
SELECT tx_nome, nr_idade
FROM   tb_usuarios
WHERE  nr_idade > (SELECT AVG(nr_idade) FROM tb_usuarios);

-- tabela derivada: subquery no FROM
SELECT * FROM (
    SELECT cd_usuario, SUM(vl_total) AS vl_total
    FROM   tb_pedidos
    GROUP BY cd_usuario
) AS resumo
WHERE vl_total > 500;

EXISTS e NOT EXISTS — testar existência

      
EXISTS retorna true assim que a subquery encontra uma única linha — não importa o valor, só a existência. Por isso é mais eficiente que IN em tabelas grandes: o PostgreSQL para na primeira linha encontrada.

      

        
IN vs EXISTS
IN: compara o valor de cada linha contra uma lista completa. EXISTS: interrompe na primeira correspondência — melhor desempenho em listas grandes ou quando a subquery é correlacionada.

        
NOT IN vs NOT EXISTS
NOT IN retorna vazio se a lista contiver um NULL. NOT EXISTS funciona corretamente com NULL — prefira-o para subqueries que podem retornar nulos.

      

      

        
exists.sql — com e sem pedido

        
-- usuários que fizeram pelo menos um pedido
SELECT tx_nome
FROM   tb_usuarios u
WHERE EXISTS (
    SELECT 1 FROM tb_pedidos p WHERE p.cd_usuario = u.id_usuario
);

-- usuários que nunca fizeram nenhum pedido
SELECT tx_nome
FROM   tb_usuarios u
WHERE NOT EXISTS (
    SELECT 1 FROM tb_pedidos p WHERE p.cd_usuario = u.id_usuario
);

💡
Dentro de um EXISTS não importa o que vem depois do SELECT — por convenção usa-se SELECT 1, já que só a existência da linha importa, não o valor.

    


    
    

      
VIEW — consultas salvas

      
Uma view é uma consulta SQL salva com um nome, que se comporta como uma tabela virtual — sem duplicar os dados. Toda vez que a view é consultada, a query original roda por trás.

      

        
view.sql

        
CREATE VIEW vw_usuarios_ativos AS
SELECT id_usuario, tx_nome, tx_email
FROM   tb_usuarios
WHERE  fl_ativo = true;

-- uso: idêntico a consultar uma tabela
SELECT * FROM vw_usuarios_ativos;

        
✓ CREATE VIEW — "vw_usuarios_ativos" pronta para uso.

      

    


    
    

      
INDEX — acelerando buscas

      
Um índice é uma estrutura auxiliar que acelera buscas, funcionando como o índice de um livro. Acelera leituras, mas tem custo em espaço e em escrita — cada INSERT/UPDATE também atualiza o índice.

      

        
index.sql

        
CREATE INDEX idx_tb_usuarios_tx_email ON tb_usuarios(tx_email);
CREATE INDEX idx_tb_pedidos_cd_usuario ON tb_pedidos(cd_usuario);

        
✓ CREATE INDEX — buscas por "email" e "cd_usuario" ficam muito mais rápidas.

FUNCTION — código reutilizável no banco

      
Uma function é um bloco de lógica reutilizável armazenado dentro do banco: recebe parâmetros, executa comandos SQL ou PL/pgSQL e pode retornar um valor ou conjunto de linhas.

      

        
function.sql

        
CREATE FUNCTION fn_atualizar_timestamp()
RETURNS TRIGGER AS $$
BEGIN
    NEW.dt_criacao = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

        
✓ CREATE FUNCTION — "fn_atualizar_timestamp" disponível para uso em triggers.

      

    


    
    

      
TRIGGER — reações automáticas

      
Uma trigger executa uma function automaticamente antes (BEFORE) ou depois (AFTER) de um evento (INSERT, UPDATE ou DELETE) acontecer em uma tabela.

      

        
trigger.sql

        
CREATE TRIGGER trg_atualiza_data
BEFORE UPDATE ON tb_usuarios
FOR EACH ROW
EXECUTE FUNCTION fn_atualizar_timestamp();

        
✓ CREATE TRIGGER — a cada UPDATE em tb_usuarios, a função é disparada automaticamente.

      

    


    
    

      
VACUUM — limpeza e manutenção

      
O PostgreSQL usa MVCC (controle de concorrência multiversão): ao fazer UPDATE ou DELETE, a linha antiga não é apagada imediatamente — fica marcada como "morta". O VACUUM libera esse espaço e atualiza as estatísticas usadas pelo otimizador.

      

        
🧹 VACUUM
Marca espaço das linhas mortas como reutilizável. Não devolve espaço ao SO. Não bloqueia leituras.

        
🗜️ VACUUM FULL
Reescreve a tabela inteira e devolve espaço ao SO. Bloqueia a tabela durante a execução.

        
📊 VACUUM ANALYZE
Faz o VACUUM padrão e atualiza estatísticas — as mesmas que o planejador usa para escolher o plano.

      

      

        
vacuum.sql

        
VACUUM ANALYZE tb_usuarios;

        
✓ VACUUM — espaço morto liberado e estatísticas atualizadas.

      

      
⚠️
VACUUM FULL bloqueia a tabela durante a execução — evite em produção com alto tráfego. No dia a dia, o autovacuum (processo em segundo plano do PostgreSQL) já cuida da manutenção automaticamente.

    


    
    

      
Backup e restauração

      
Um backup é uma cópia de segurança dos dados — essencial para recuperar o banco em caso de erro humano (um DELETE sem WHERE), falha de hardware ou corrupção. pg_dump e psql são as ferramentas de linha de comando do PostgreSQL.

      

        
🛡️ pg_dump
Backup lógico de um único banco de dados — tabelas, dados, views, functions…

        
🗄️ pg_dumpall
Backup de todos os bancos do servidor, incluindo roles e permissões globais.

        
♻️ pg_restore / psql
Restauram um backup gerado pelo pg_dump, recriando estrutura e dados.

      

      

        
terminal — backup e restauração

        
# backup em formato .sql (legível)
pg_dump -U postgres -d minha_base -f backup.sql

# backup em formato custom (compactado, restauração seletiva)
pg_dump -U postgres -d minha_base -F c -f backup.dump

# restaurar .sql
psql -U postgres -d minha_base_nova -f backup.sql

# restaurar .dump
pg_restore -U postgres -d minha_base_nova --clean backup.dump

        
✓ Backup e restauração executados com sucesso.

      

      
💡
Boas práticas: automatize os backups, teste a restauração periodicamente — um backup nunca testado é um backup que você não sabe se funciona — e armazene as cópias em local diferente do servidor original.
