Do código ao servidor: subindo seu projeto em produção

Redes, Linux, SSH, chaves, Docker, Compose, proxy reverso, HTTPS, CI/CD e escala horizontal, na ordem em que você precisa aprender para colocar uma aplicação no ar com segurança.

Visão geral e roteiro

Subir um projeto é encadear peças: um computador remoto (servidor), um jeito seguro de entrar nele (SSH), um jeito padronizado de empacotar a aplicação (Docker), um jeito de expô-la para a internet (rede, DNS, proxy, HTTPS) e um jeito de repetir tudo isso sem dor (CI/CD). Este guia segue essa ordem.

O caminho de uma requisição

fluxo.txt
# do navegador até o seu código
Usuário → DNS (meuapp.com → 203.0.113.10)
        → Firewall do servidor (portas 80/443)
        → Proxy reverso (Nginx / Caddy / Traefik) + HTTPS
        → Container da aplicação (porta 8080)
        → Container do banco (rede interna, sem exposição pública)

Roteiro em ordem de conhecimento

Base

1. Linux + Redes

Terminal, permissões, processos, IP, porta, DNS, TCP, HTTP, firewall. Sem isso, nada do resto faz sentido.

Acesso

2. Servidor + SSH

Contratar uma VPS, entrar por chave SSH, criar usuário sem root e fechar portas desnecessárias.

Empacotar

3. Docker + Compose

Transformar a aplicação em imagem, orquestrar app + banco + proxy em um único arquivo.

Expor

4. Domínio + HTTPS

Apontar DNS, configurar proxy reverso e certificado Let's Encrypt.

Automatizar

5. CI/CD

Build e deploy automáticos a cada push, com registry de imagens.

Crescer

6. Escala + Observabilidade

Várias réplicas atrás de um load balancer, logs, métricas, backup.

💡
Dica: faça o primeiro deploy do jeito mais simples possível (1 VPS + Docker Compose). Só pense em Kubernetes ou múltiplos servidores quando houver um problema real de carga ou disponibilidade.

Linux e terminal

Quase todo servidor roda Linux (Ubuntu Server e Debian são as escolhas mais comuns). Você vai administrá-lo por terminal, sem interface gráfica.

Comandos de navegação e arquivos

Comando Para que serve
pwd Mostra o diretório atual.
ls -lah Lista arquivos com permissões, tamanho legível e ocultos.
cd /caminho Entra em um diretório. cd ~ vai para a home.
mkdir -p a/b/c Cria diretórios (e os pais, se faltarem).
cp -r origem destino Copia arquivos ou pastas.
mv origem destino Move ou renomeia.
rm -rf pasta Apaga sem perguntar. Cuidado: não tem lixeira.

Usuários, permissões e sudo

Cada arquivo tem dono, grupo e permissões de leitura (r=4), escrita (w=2) e execução (x=1) para dono, grupo e outros. chmod 640 = dono lê/escreve, grupo lê, outros nada.

terminal
ls -l id_ed25519
chmod 600 id_ed25519     # só o dono lê e escreve
chown deploy:deploy app/ -R  # troca dono e grupo
sudo apt update            # executa como administrador
-rw------- 1 deploy deploy 411 out 9 15:00 id_ed25519

Processos, serviços, disco e pacotes

terminal
ps aux | grep java       # processos
top / htop                 # uso de CPU e memória
df -h                     # espaço em disco
free -h                   # memória RAM
systemctl status docker   # estado de um serviço
systemctl enable --now docker
journalctl -u docker -f   # logs de um serviço
sudo apt update && sudo apt upgrade -y
💡
Regra de ouro: nunca rode a aplicação como root. Crie um usuário comum, dê sudo só se precisar e use esse usuário no dia a dia.

Redes e network

Entender rede é o que separa "copiei um tutorial" de "sei por que não está funcionando". Estes são os conceitos que aparecem em todo deploy.

Endereço

IP

Identifica uma máquina na rede. IPv4 (203.0.113.10) ou IPv6. Pode ser público (alcançável da internet) ou privado (10.x, 172.16–31.x, 192.168.x, só dentro da rede).

Porta

Porta

Número de 0 a 65535 que identifica qual serviço na máquina. IP é o prédio, porta é o apartamento.

Nomes

DNS

Traduz meuapp.com em IP. Registros comuns: A (IPv4), AAAA (IPv6), CNAME (alias), MX (e-mail), TXT (verificações).

Transporte

TCP e UDP

TCP garante entrega e ordem (HTTP, SSH, bancos). UDP é mais rápido e sem garantias (DNS, vídeo, jogos).

Portas que você vai usar

Porta Serviço Expor à internet?
22 SSH (acesso administrativo) Sim, mas restrito (chave, sem senha, idealmente por IP)
80 HTTP Sim (redireciona para 443)
443 HTTPS Sim
5432 PostgreSQL Não. Só rede interna
3306 MySQL / MariaDB Não. Só rede interna
6379 Redis Não. Só rede interna
8080 Porta comum de apps (Quarkus, Spring) Não direto: atrás do proxy

Conceitos de rede que causam dúvida

Firewall

Regras que decidem quais portas aceitam conexão. Princípio: bloqueie tudo e libere só o necessário.

NAT

Permite que vários dispositivos de uma rede privada saiam para a internet com um único IP público. O Docker usa NAT para os containers.

Proxy reverso

Fica na frente das aplicações, recebe as requisições e as repassa ao container certo, cuidando de HTTPS.

Load balancer

Distribui requisições entre várias instâncias da mesma aplicação (ver capítulo de escala).

CIDR / sub-rede

10.0.0.0/24 significa 256 endereços (10.0.0.0 a 10.0.0.255). Usado em redes privadas e no Docker.

Latência e banda

Latência é o tempo de ida e volta; banda é a quantidade por segundo. Servidor longe do usuário = mais latência.

Comandos de diagnóstico de rede

terminal
ip a                          # interfaces e IPs da máquina
ping -c 3 meuapp.com           # o host responde?
dig +short meuapp.com          # qual IP o DNS devolve?
ss -tulpn                      # quais portas estão escutando e quem escuta
curl -I https://meuapp.com     # cabeçalhos HTTP
nc -zv servidor 5432          # a porta está acessível?
traceroute meuapp.com          # caminho até o destino
$ dig +short meuapp.com
203.0.113.10

$ curl -I https://meuapp.com
HTTP/2 200
server: nginx
content-type: application/json
⚠️
Atenção: "a porta está aberta no servidor" não é o mesmo que "a porta está acessível da internet". Podem existir três camadas bloqueando: firewall do provedor (security group), firewall do sistema (ufw) e o próprio serviço escutando só em 127.0.0.1.

Servidores

Servidor é só um computador ligado 24h com IP fixo. Você pode alugar um pedaço dele (VPS), usar serviços gerenciados na nuvem ou até manter um físico.

Mais simples

VPS

Máquina virtual com acesso total (root). Exemplos: Hetzner, DigitalOcean, Contabo, Hostinger, Locaweb. Ótima para começar: preço fixo e controle completo.

Escalável

Nuvem (IaaS)

AWS EC2, Google Compute Engine, Azure VM, Oracle Cloud. Mais recursos (load balancer, redes privadas, autoscaling), curva de aprendizado e cobrança por uso.

Menos trabalho

PaaS / gerenciados

Render, Railway, Fly.io, Cloud Run, Heroku. Você envia a imagem ou o código e eles cuidam do servidor. Mais caro em escala e menos controle.

Hardware próprio

On-premise

Servidor físico na empresa. Exige IP fixo, no-break, backup e segurança por sua conta.

Como escolher o tamanho

Recurso O que observar
CPU (vCPU) Processamento. APIs simples funcionam bem com 1–2 vCPUs.
RAM Principal gargalo em apps Java: considere 1 GB+ por JVM, mais o banco. Com Quarkus nativo o consumo cai bastante. Comece com 2–4 GB para app + banco.
Disco SSD/NVMe. Imagens Docker, logs e dados do banco crescem: 40 GB+ é um começo razoável.
Região Escolha perto dos usuários (latência) e atenda requisitos da LGPD.
Tráfego Veja a franquia mensal de transferência e o preço do excedente.

Escala vertical x horizontal (prévia)

Vertical: trocar por uma máquina maior (mais CPU/RAM). Simples, mas tem teto e exige reinício. Horizontal: adicionar mais máquinas/instâncias e dividir a carga. Mais complexa, mas sem teto prático e tolera falhas. Veja o capítulo 15.

💡
Ao criar a VPS: escolha Ubuntu LTS (22.04 ou 24.04), adicione sua chave pública SSH no painel do provedor e anote o IP público. Isso já deixa o servidor pronto para o próximo capítulo.

SSH e chaves pública/privada

SSH (Secure Shell) é o protocolo para controlar um servidor remoto por terminal, com tráfego criptografado. Em vez de senha, o padrão profissional é usar um par de chaves.

Como funciona o par de chaves

Secreta

Chave privada

Fica somente no seu computador (~/.ssh/id_ed25519). Nunca envie, nunca commite, nunca cole em chat. Quem a tem, entra como você.

Compartilhável

Chave pública

Arquivo .pub. Você a coloca no servidor, em ~/.ssh/authorized_keys. Pode ser divulgada sem risco.

Ao conectar, o servidor desafia o cliente: só quem tem a chave privada correspondente à pública cadastrada consegue provar quem é, sem a chave privada trafegar pela rede.

fluxo-ssh.txt
1. Cliente  → Servidor: "quero entrar como deploy"
2. Servidor → Cliente: "prove que tem a chave privada da pública que eu conheço" (desafio)
3. Cliente  → assina o desafio com a chave privada
4. Servidor → verifica a assinatura com a chave pública → acesso liberado

Gerando e instalando a chave

no seu computador 
# 1) gerar o par (Ed25519 é o algoritmo recomendado hoje)
ssh-keygen -t ed25519 -C "meu-notebook"

# 2) copiar a pública para o servidor
ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@203.0.113.10

# 3) entrar
ssh deploy@203.0.113.10
Generating public/private ed25519 key pair.
Enter passphrase (empty for no passphrase): ********
Your identification has been saved in /home/voce/.ssh/id_ed25519
Your public key has been saved in /home/voce/.ssh/id_ed25519.pub

deploy@servidor:~$ conectado ✓
⚠️
Use passphrase na chave privada. Se o notebook for roubado, a passphrase é a última barreira. Use ssh-agent para digitá-la uma vez por sessão.

Arquivo ~/.ssh/config: atalhos

~/.ssh/config
Host producao
  HostName 203.0.113.10
  User deploy
  Port 22
  IdentityFile ~/.ssh/id_ed25519

# agora basta:  ssh producao

Comandos úteis com SSH

Comando Função
ssh producao "docker ps" Executa um comando remoto e volta.
scp arquivo.jar producao:/home/deploy/ Copia arquivo para o servidor.
rsync -avz ./dist/ producao:/srv/app/ Sincroniza pastas, enviando só o que mudou.
ssh -L 5433:localhost:5432 producao Túnel SSH: acessa o Postgres do servidor em localhost:5433 sem expor a porta 5432 na internet.
ssh-keyscan host >> ~/.ssh/known_hosts Registra a identidade do servidor (útil em CI).
🚫
Nunca commite chaves privadas, .env ou tokens no Git. Se isso acontecer, considere a chave comprometida: gere outra, remova a antiga do servidor e revogue o que foi exposto.

Chaves em deploy automatizado

Para o GitHub Actions entrar no servidor, crie uma chave exclusiva para deploy (sem passphrase, só para isso), instale a pública no servidor e guarde a privada como secret do repositório. Se vazar, você revoga só essa chave.

Segurança inicial do servidor

Um servidor novo na internet começa a receber tentativas de invasão em minutos. Faça este "endurecimento" antes de instalar qualquer coisa.

Passo a passo

primeiro acesso (como root)
# 1) atualizar o sistema
apt update && apt upgrade -y

# 2) criar usuário comum com sudo
adduser deploy
usermod -aG sudo deploy

# 3) copiar sua chave pública para esse usuário
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy

# 4) firewall: liberar SSH, HTTP e HTTPS; bloquear o resto
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable

# 5) proteger contra força bruta
apt install -y fail2ban unattended-upgrades

Endurecendo o SSH

Edite /etc/ssh/sshd_config (teste a chave em outra janela antes de desativar a senha, para não se trancar para fora):

/etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
# depois:  sudo systemctl restart ssh
⚠️
Docker e ufw: portas publicadas pelo Docker (-p 5432:5432) ignoram o ufw, porque o Docker mexe direto no iptables. Se publicar uma porta, ela fica aberta ao mundo. Publique só 80/443 (via proxy) ou use 127.0.0.1:5432:5432.

Checklist rápido de segurança

✅ Faça

Login só por chave · usuário sem root · firewall ativo · atualizações automáticas · banco sem porta pública · backups testados · senhas longas e únicas.

❌ Evite

Rodar app como root · expor banco/Redis · senhas padrão · deixar painéis administrativos abertos · guardar segredos no Git.

Conceitos do Docker

Docker empacota a aplicação com tudo o que ela precisa (runtime, libs, configuração) em uma imagem. Quem roda essa imagem obtém o mesmo comportamento em qualquer lugar, acabando com o "na minha máquina funciona".

Receita

Imagem

Modelo imutável e em camadas (aplicação + dependências). É o "molde". Identificada por nome:tag, ex.: postgres:16.

Em execução

Container

Instância em execução de uma imagem, isolada do resto. Descartável: se morrer, sobe outro igual.

Armazém

Registry

Repositório de imagens: Docker Hub, GitHub Container Registry (ghcr.io), AWS ECR, etc. Você faz push do build e o servidor faz pull.

Dados

Volume

Armazenamento que sobrevive ao container. Tudo que está dentro do container e fora de um volume é perdido ao recriá-lo.

Container x máquina virtual

Máquina virtual Container
Isolamento SO completo por VM Compartilha o kernel do host
Tamanho GBs MBs
Inicialização Minutos Segundos ou menos
Uso típico Servidor inteiro Uma aplicação ou serviço

Instalando o Docker no Ubuntu

servidor
# script oficial (confira em docs.docker.com antes de usar em produção)
curl -fsSL https://get.docker.com | sudo sh

# usar docker sem sudo (relogue depois)
sudo usermod -aG docker deploy

docker --version
docker compose version
⚠️
Estar no grupo docker equivale, na prática, a ter acesso root à máquina. Dê esse acesso só a quem precisa.

Comandos essenciais do Docker

Estes comandos cobrem 90% do dia a dia. Aprenda-os na ordem: rodar → inspecionar → entrar → limpar.

Rodar containers

terminal
docker run -d \
  --name meu-postgres \
  -e POSTGRES_PASSWORD=segredo \
  -p 127.0.0.1:5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  --restart unless-stopped \
  postgres:16
Unable to find image 'postgres:16' locally
16: Pulling from library/postgres
Status: Downloaded newer image for postgres:16
3f9a1c2b7d4e... (ID do container)
Flag Significado
-d Roda em segundo plano (detached).
--name Nome do container, para referenciá-lo.
-p host:container Publica porta. 127.0.0.1:5432:5432 expõe só localmente.
-e CHAVE=valor Define variável de ambiente.
-v origem:destino Monta volume ou pasta do host.
--restart unless-stopped Sobe de novo após queda ou reboot do servidor.
--network Conecta a uma rede Docker específica.
--rm Remove o container ao terminar (bom para tarefas pontuais).
-m 512m --cpus 1 Limita memória e CPU.

Inspecionar e depurar

terminal
docker ps                      # containers rodando (-a: todos)
docker logs -f --tail 100 app   # acompanhar logs
docker exec -it app sh          # abrir um shell dentro do container
docker inspect app              # detalhes completos (IP, mounts, env)
docker stats                    # CPU/RAM em tempo real
docker top app                  # processos do container

Ciclo de vida

terminal
docker stop app   && docker start app
docker restart app
docker rm -f app               # remove container
docker pull nginx:stable        # baixa imagem
docker images                  # lista imagens locais
docker rmi imagem:tag          # remove imagem
docker build -t meuapp:1.0 .    # constrói imagem a partir do Dockerfile
docker login ghcr.io
docker tag meuapp:1.0 ghcr.io/usuario/meuapp:1.0
docker push ghcr.io/usuario/meuapp:1.0

Limpeza

terminal
docker system df                 # quanto espaço o Docker usa
docker container prune            # remove containers parados
docker image prune -a             # remove imagens sem uso
docker volume prune               # CUIDADO: apaga volumes sem container
🚫
docker volume prune e docker system prune --volumes podem apagar dados de banco que estavam em volumes de containers parados. Confira antes.

Dockerfile: empacotando a aplicação

O Dockerfile é a receita para construir a imagem. Cada instrução cria uma camada com cache: ordene do que muda menos (dependências) para o que muda mais (seu código) para builds rápidos.

Instrução Função
FROM Imagem base.
WORKDIR Diretório de trabalho dentro da imagem.
COPY Copia arquivos do projeto para a imagem.
RUN Executa comando durante o build (instalar, compilar).
ENV Define variáveis de ambiente padrão.
EXPOSE Documenta a porta usada (não publica por si só).
USER Usuário que executa o processo (evite root).
CMD / ENTRYPOINT Comando executado ao iniciar o container.

Exemplo: API Java/Quarkus com multi-stage build

O multi-stage compila em uma imagem pesada (JDK + Maven) e copia só o resultado para uma imagem final leve. A imagem de produção não carrega ferramentas de build.

Dockerfile
# ---------- Estágio 1: build ----------
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn -B dependency:go-offline        # camada de dependências (cacheada)
COPY src ./src
RUN mvn -B package -DskipTests

# ---------- Estágio 2: runtime ----------
FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -r -u 1001 appuser
COPY --from=build --chown=appuser /build/target/quarkus-app/ ./
USER appuser
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "quarkus-run.jar"]

Outro exemplo: front-end React servido por Nginx

Dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:stable-alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

.dockerignore

Evita enviar arquivos desnecessários (e segredos) ao build:

.dockerignore
.git
node_modules
target
.env
*.log
💡
Boas práticas: fixe versões de imagem (postgres:16, não latest) · prefira imagens slim/alpine · rode como usuário sem root · uma responsabilidade por container · nunca coloque senhas no Dockerfile.

Docker Compose

Aplicações reais têm vários serviços (app, banco, cache, proxy). O Compose descreve todos em um arquivo compose.yaml e sobe tudo com um comando.

compose.yaml
services:
  api:
    image: ghcr.io/usuario/minha-api:1.0
    restart: unless-stopped
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    networks: [backend, web]
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/q/health/ready"]
      interval: 30s
      retries: 3

  db:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [backend]            # sem ports: não fica exposto
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 10s
      retries: 5

networks:
  backend:
  web:

volumes:
  pgdata:

Comandos do Compose

terminal
docker compose up -d                # sobe tudo em segundo plano
docker compose ps                   # estado dos serviços
docker compose logs -f api          # logs de um serviço
docker compose pull && docker compose up -d   # atualizar imagens
docker compose exec db psql -U app appdb
docker compose down                 # derruba (mantém volumes)
docker compose down -v              # derruba e APAGA volumes
docker compose config               # valida e mostra o arquivo final
[+] Running 3/3
✔ Network app_backend Created
✔ Container app-db-1 Healthy
✔ Container app-api-1 Started
⚠️
depends_on sozinho só controla a ordem de início, não se o banco está pronto. Combine com healthcheck + condition: service_healthy, como acima.

Redes e volumes no Docker

Aqui os conceitos de rede do capítulo 3 aparecem na prática. Entender isso evita o erro clássico connection refused entre containers.

Tipos de rede

Driver Como funciona Quando usar
bridge Rede privada virtual no host, com NAT e DNS interno por nome de container. Padrão, para um único servidor.
host Container usa diretamente a rede do host, sem isolamento. Casos raros de performance ou portas dinâmicas.
none Sem rede. Tarefas totalmente isoladas.
overlay Rede que atravessa vários servidores (Swarm/Kubernetes). Escala horizontal em múltiplos hosts.

Regras que resolvem 90% dos problemas

Regra 1

Container fala com container pelo nome

Na mesma rede, a API acessa o banco em jdbc:postgresql://db:5432/appdb. Use o nome do serviço, nunca localhost.

Regra 2

localhost é o próprio container

Dentro do container, localhost é ele mesmo, não o host nem outros containers.

Regra 3

Porta interna x publicada

ports: "8081:8080" → de fora, 8081; dentro da rede Docker, continua 8080. Containers entre si usam a porta interna.

Regra 4

Só publique o necessário

Banco e cache ficam sem ports. Só o proxy publica 80/443.

Comandos de rede e volume

terminal
docker network ls
docker network create web
docker network inspect app_backend
docker volume ls
docker volume inspect pgdata

# backup simples de um volume
docker run --rm -v pgdata:/dados -v $(pwd):/backup alpine \
  tar czf /backup/pgdata.tar.gz -C /dados .

Volume nomeado x bind mount

Tipo Exemplo Uso
Volume nomeado pgdata:/var/lib/postgresql/data Dados persistentes gerenciados pelo Docker (bancos).
Bind mount ./nginx.conf:/etc/nginx/nginx.conf:ro Arquivo/pasta do host (configurações, desenvolvimento).

Domínio, proxy reverso e HTTPS

Para usuários acessarem https://api.meuapp.com você precisa de três coisas: DNS apontando para o servidor, um proxy reverso recebendo 80/443 e um certificado TLS.

1. Apontar o DNS

Tipo Nome Valor
A api 203.0.113.10 (IP do servidor)
A @ (raiz) 203.0.113.10
CNAME www meuapp.com

A propagação pode levar de minutos a horas. Confira com dig +short api.meuapp.com.

2. Proxy reverso: a opção mais simples é o Caddy

O Caddy obtém e renova certificados Let's Encrypt sozinho. Alternativas: Nginx (clássico, mais configuração + Certbot) e Traefik (descobre containers por labels, bom com Docker).

Caddyfile
api.meuapp.com {
    reverse_proxy api:8080
}

meuapp.com {
    reverse_proxy frontend:80
}
compose.yaml (trecho)
  caddy:
    image: caddy:2
    restart: unless-stopped
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
    networks: [web]

Equivalente em Nginx

nginx.conf
server {
    listen 80;
    server_name api.meuapp.com;
    location / {
        proxy_pass http://api:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

3. Como o HTTPS funciona

TLS

Criptografa a conexão entre navegador e servidor, evitando leitura e alteração no caminho.

Certificado

Prova que o domínio é seu. A Let's Encrypt emite de graça, válido por 90 dias, com renovação automática.

Desafio HTTP-01

A Let's Encrypt acessa a porta 80 do seu domínio para validar. Por isso DNS e porta 80 precisam estar corretos.

⚠️
Atrás de um proxy, a aplicação enxerga o IP do proxy, não o do usuário. Configure o uso dos cabeçalhos X-Forwarded-* (no Quarkus: quarkus.http.proxy.proxy-address-forwarding=true).

Deploy e CI/CD

CI (integração contínua) compila e testa a cada push. CD (entrega contínua) publica automaticamente. Resultado: deploy vira "dar merge na main".

Estratégias de deploy

Manual

SSH + git pull + build

Entra no servidor e roda os comandos. Serve para aprender, mas é lento e sujeito a erro.

Recomendado

Build no CI + registry + pull

O pipeline constrói a imagem, envia ao registry e o servidor só baixa e reinicia. Rápido e reproduzível.

Zero downtime

Rolling update

Sobe a nova versão, espera ficar saudável e só então derruba a antiga.

Cuidadoso

Blue/Green e Canary

Blue/green mantém dois ambientes e troca o tráfego. Canary libera a versão nova para uma fração pequena dos usuários primeiro.

Exemplo: GitHub Actions

.github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

      - name: Deploy via SSH
        env:
          KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          HOST: ${{ secrets.DEPLOY_HOST }}
        run: |
          install -m 600 /dev/null key
          echo "$KEY" > key
          ssh -i key -o StrictHostKeyChecking=accept-new deploy@$HOST \
            "cd /srv/app && docker compose pull && docker compose up -d"
💡
Tag por commit: use o SHA (ou versão) como tag da imagem em vez de só latest. Assim você sabe exatamente o que está no ar e consegue fazer rollback trocando a tag e rodando docker compose up -d.

Pipeline saudável

1. Test

Testes unitários e de integração.

2. Build

Imagem Docker com tag única.

3. Push

Envia ao registry.

4. Deploy

Servidor baixa, sobe e verifica o health check.

⚠️
Migrações de banco: a nova versão do código pode rodar enquanto a antiga ainda existe. Faça migrações compatíveis com as duas versões (adicione colunas antes de remover). Ferramentas: Flyway, Liquibase.

Escala horizontal

Escalar é lidar com mais carga sem cair. Existem dois caminhos, e quase sempre você começa pelo mais simples.

Vertical (scale up)

Máquina maior

Mais CPU, RAM, disco. Prós: zero mudança de código, simples. Contras: tem teto, exige reinício e continua sendo um único ponto de falha.

Horizontal (scale out)

Mais instâncias

Várias cópias da aplicação dividindo a carga. Prós: quase sem teto, tolera falha de uma instância. Contras: exige aplicação preparada e infraestrutura extra.

Arquitetura típica

arquitetura.txt
                    ┌──► API réplica 1 ──┐
Usuários → Load Balancer ──► API réplica 2 ──┼──► Banco (primário + réplicas de leitura)
                    └──► API réplica 3 ──┤──► Cache (Redis)
                                              └──► Fila (RabbitMQ / Kafka)

Pré-requisito: aplicação stateless

Para escalar horizontalmente, qualquer réplica precisa atender qualquer requisição. Isso significa que a aplicação não guarda estado local:

Estado local (problema) Solução externa
Sessão de usuário na memória JWT (token) ou sessão no Redis
Arquivos enviados gravados em disco local Object storage (S3, MinIO, R2)
Cache em memória da JVM compartilhado entre usuários Cache distribuído (Redis)
Tarefas agendadas (@Scheduled / cron) dentro do app Executar só em 1 instância, lock distribuído (ex.: Quartz clusterizado) ou job separado
Filas e processamento em memória Broker externo (RabbitMQ, Kafka, SQS)
Configuração fixa no código Variáveis de ambiente / serviço de configuração
⚠️
Tarefas agendadas duplicam: com 3 réplicas, um job "a cada minuto" roda 3 vezes por minuto. Isso causa envios duplicados (e-mails, notificações push, cobranças). Decida qual instância executa o job ou use lock distribuído.

Balanceamento de carga

Round robin

Revezamento simples entre as instâncias.

Least connections

Envia para quem tem menos conexões ativas. Bom para requisições de duração variável.

IP hash / sticky

Mesmo cliente → mesma instância. Muleta para apps com estado; prefira ser stateless.

nginx.conf (upstream)
upstream api_pool {
    least_conn;
    server 10.0.0.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 backup;
}
server {
    listen 80;
    location / { proxy_pass http://api_pool; }
}

Escalando com Docker

No Compose, é possível rodar várias réplicas no mesmo servidor (útil para aproveitar CPU e ter zero-downtime). Para vários servidores, você precisa de um orquestrador.

terminal
# 3 réplicas da API no mesmo host (remova container_name e ports fixos)
docker compose up -d --scale api=3

# Docker Swarm: orquestração simples em vários servidores
docker swarm init
docker stack deploy -c compose.yaml app
docker service scale app_api=5
[+] Running 3/3
✔ Container app-api-1 Started
✔ Container app-api-2 Started
✔ Container app-api-3 Started
Orquestrador Quando faz sentido
Docker Compose 1 servidor. Começo e a maioria dos projetos pequenos/médios.
Docker Swarm Poucos servidores, equipe pequena, curva de aprendizado baixa.
Kubernetes Muitos serviços, autoscaling, equipes grandes. Poderoso, porém complexo (versões gerenciadas: GKE, EKS, AKS, DOKS).
Serverless / Cloud Run Você entrega a imagem; a plataforma escala (inclusive a zero).

E o banco de dados?

O banco costuma ser o verdadeiro gargalo. Em ordem de esforço: otimizar queries e índices → pool de conexões (cuidado: N réplicas × pool = muitas conexões) → cache (Redis) → réplicas de leitura → particionamento/sharding. Só use banco clusterizado quando as etapas anteriores não bastarem.

💡
Quando escalar? Meça antes: CPU sustentada acima de ~70%, memória no limite, latência p95 subindo, filas crescendo. Escalar sem medir é gastar dinheiro no lugar errado. Ferramentas de teste de carga: k6, JMeter, Gatling.

Alta disponibilidade

Elimine pontos únicos de falha

2+ instâncias da app, load balancer redundante, banco com réplica e failover, backups em outro local.

Health checks

O load balancer só envia tráfego a instâncias saudáveis (/q/health/live e /ready no Quarkus).

Logs, monitoramento e backup

Colocar no ar é metade do trabalho. A outra metade é saber quando algo quebra antes do usuário e conseguir recuperar quando o pior acontecer.

Logs

compose.yaml (limitar tamanho dos logs)
  api:
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
🚫
Sem limite, os logs do Docker enchem o disco e derrubam o servidor. Configure rotação. Em produção com várias réplicas, centralize os logs (Loki, ELK, Datadog, CloudWatch).

Backup: regra 3-2-1

3

Três cópias

Os dados originais mais duas cópias.

2

Duas mídias

Ex.: disco do servidor + armazenamento de objetos.

1

Uma fora do local

Outro provedor ou região, protegida contra o mesmo desastre.

backup-db.sh
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F_%H%M)
docker compose exec -T db pg_dump -U app appdb | gzip > /backups/appdb_$STAMP.sql.gz
find /backups -name '*.sql.gz' -mtime +14 -delete   # retenção de 14 dias
# depois: enviar para fora do servidor (rclone / rsync / aws s3 cp)

# agendar no cron (crontab -e):  todo dia às 03:00
# 0 3 * * * /srv/app/backup-db.sh
⚠️
Backup que nunca foi restaurado não é backup. Teste a restauração periodicamente, em um ambiente separado.
